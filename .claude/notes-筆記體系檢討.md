# 筆記體系檢討（暫存）

> 日期：2026-08-16
> 用途：本專案結案後，回頭看用於下個專案（SDD）的筆記體系設計輸入。
> 這不是本專案要動的規劃，只是 Amber 與 Claude 的閒聊整理。

---

## 起因

本專案（vibe coding）目前只有一份 `.claude/current-handoff.md` 承載所有跨 session 記憶，500+ 行。Amber 觀察到「印象中已經做了」的自我核對很有價值，但 session 開始要讀的東西越來越多，開始想「下個專案的筆記體系該怎麼設計比較理想」。

## 現況 handoff.md 實際承載的資訊類型（比「規格+破口修正」多）

1. **當前狀態**（頻繁變）：已完成功能、build/migration、DB 現況、下一步候補
2. **架構狀態**（漸增）：已落地 pattern、邏輯落點（Domain / App Service / Middleware 各層放什麼、為什麼）、有無偏離 CLAUDE.md、後續可能優化
3. **已定案的設計決策**（累積、不太動）：使用者、帳號生命週期、緊急存取帳號、報銷單生命週期擴充、預支款與零用金、結清紀錄……「拍板過的東西，下次別再重新設計」
4. **推翻紀錄**：曾經定案後來取消（自助註冊、零用金當預支款、預支款用途分類），**都留一句「為什麼推翻」**——沒有這個下 session 很可能又提議一次同樣的設計
5. **驗證軌跡**：已實測繞過畫面的側門（直接 POST 送審別人的草稿、Butter 刪 amber 的草稿……）
6. **開發環境細節**：user secrets、PostgreSQL scoop 服務註冊、psql 疑難排解、EF migration 陷阱

「規格」屬於 1+3；「破口修正」多半散在 1（已完成功能）與 4（推翻的原因）。

## 核心診斷：讀取用途分兩類，混一起看不出來

- **必讀類**：不知道會撞到什麼陷阱。「這個功能是不是做過」「這個設計是不是被推翻過」「Domain 該不該裝這條規則」——**沒讀到就會做錯**。
- **按需查類**：知道自己要動什麼、只查那部分。「新加 migration」才查 EF 陷阱、「換機器」才查 user secrets——**沒讀到不會做錯，只是效率低**。

現在兩類混在一起，AI 為了防範必讀類漏掉，每次得把按需查類也掃一遍。這是主要痛點。

## 下個專案設計原則：從「session 開始要回答什麼問題」倒推

不是「該有哪些檔」，是「AI 每 session 開頭要能回答哪些問題」，倒推出檔案結構。必答問題大概是：

- **Q1 現在做到哪、下一步是什麼？**（進度）
- **Q2 有什麼地雷不能踩？**（推翻過的設計、已定案的紅線）
- **Q3 系統做了什麼、還沒做什麼？**（「這件不是做過了嗎」的自我核對）
- **Q4 我要動的東西該放哪一層？**（架構規範）
- **Q5 開發環境有陷阱嗎？**（環境細節）

Q1+Q2+Q3 是必答，Q4 是有動 code 才需要，Q5 是撞到才需要。三層拆檔自然浮現：**必讀（薄）／需求動代碼才讀／撞到才讀**。這比「按主題切」（架構、決策、環境）更能反映實際讀取需求。

## 這個專案實際踩過的痛點（下個專案的直接輸入）

- **推翻紀錄要「看標題就避開」**：Claude 這個 session 差點又提「附件上傳」——handoff 上要往下讀才看到被推翻。下次紅線用「一句話警告清單」放最頂端，理由連結出去。
- **「還沒做」不要分散在三處**：目前散在「已知缺口 / 應用面候補 / 開發環境待辦」三個章節。統一成「未做清單 + 每項標『已排除／待排／不做』」。
- **「已完成」要方便自我核對**：`按時間堆疊寫` 不利於「模組視角」的核對。下次按主題 / 模組整理（帳號、報銷單、預支款、專案、報表……），讓「這個模組做過什麼」一眼看完。
- **驗證軌跡（側門測試）越積越多但幾乎不回頭讀**：獨立成 `verification-log.md`，handoff 只留最新一句「XX 已補驗」。

## 另一個抽象觀察：時間性 vs 決策性資訊

Handoff 的本質問題是**把「時間性資訊」（現在如何）與「決策性資訊」（為什麼這樣）混在一起**。

- **時間性**會過期、需要頻繁改寫
- **決策性**不會（除非被推翻）、寫完就凍結

兩者維護節奏完全不同。做一個功能，時間性資訊要更新四五處（狀態、build、DB、下一步），決策性資訊可能一處都不動——但因為同檔，每次都要滑過決策段落確認「沒有需要一併改的地方嗎」。**下個專案的核心設計原則：時間性與決策性分檔**。這比「按主題」或「按 layer」更貼近實際維護痛點。

## AI 自檢清單機制（一個沒被試過的點子）

必讀檔頂端可加一段自檢清單，讓 AI 回答完才動手：

```
開工前自檢：
- [ ] 我知道當前正在做的工作是什麼？
- [ ] 我知道推翻過哪些設計，避免再提議？
- [ ] 我要動的內容是否在 spec 覆蓋範圍內？若否，是否要先擴充 spec？
- [ ] 我要動的內容是否有相關的已完成功能可能被影響？
```

在 vibe coding 也可用；在 SDD 更有意義——「是否要先擴充 spec」是 SDD 特有的判斷點。

## SDD（Spec-Driven Development）簡述

**spec 是輸入、code 是輸出**。順序是「寫規格 → 從規格拆 tasks → 實作 → 對照規格驗收」，跟 vibe coding「邊做邊記」倒過來。

跟 vibe coding 的對比：
- **Vibe coding**：腦中有大概方向 → 邊做邊決定細節 → 事後記錄「原來我們決定 XX」
- **SDD**：先跟 AI 對出規格條款寫進 spec.md → 每一條規格對應一段 code → 實作時規格是「權威事實」

SDD 適合「已經知道要做什麼」的情境（本專案 vibe coding 已幫她想清楚），不適合「要邊做邊探索需求」的階段。

## 「不用另外整理 spec」的三個機制

Amber 直覺很準：spec 若事後整理，一定會像現在 handoff 一樣不同步、被跳過。**讓 spec 天然跟開發同步**，靠三個機制：

### (a) 一律「spec 先動、code 後動」

每個新功能 session 的順序：**先跟 AI 對一次規格，寫進 spec.md → 再實作**。跟本專案「先問方向、確認才動」是同一種節奏，只是把「確認的方向」寫成 spec 條款而不是留在對話裡。做完後 spec 已是最新，不用回頭整理。

**信號**：session 開始若 AI 想動 code 前先問「這條該加進 spec 哪一節」，就對了。

### (b) spec 用「條款編號 + checkbox」結構，不是散文

散文的 spec 事後對不上實作、也不知道還沒做什麼。條款編號讓 commit / handoff / issue 都能引用，checkbox 就是「已完成功能」的權威清單，不用在 handoff 另外抄。

範例骨架：

```markdown
# ExpenseSystem 規格 v0.3

## 1. 詞彙
- 主管 / 員工 / 日常主管 / 緊急存取帳號 / …

## 2. 帳號
### 2.1 帳號生命週期
- [x] 帳號只有主管在使用者管理頁建立
- [x] 帳號兩態：Active / Disabled
- [x] 每次建立 / 重設密碼後首次登入強制改密碼
- [ ] （未實作）批次匯入帳號

### 2.2 登入
- [x] 先驗密碼、再判狀態（避免帳號列舉）
- [x] 使用者管理頁顯示最後登入時間

## 3. 報銷單
### 3.1 生命週期
- [x] 7 個狀態 …
- [x] 主管作廢已核准單 = 不可撤銷終態
...

## X. 已推翻的規格（不要再提議）
- 員工自助註冊（v0.1 → v0.2 拿掉，見〈Y〉）
- 零用金當預支款（v0.1 → v0.2 拿掉，見〈Y〉）
```

**checkbox 是關鍵**——「做了什麼、沒做什麼」一眼看完，`grep - [ ]` 秒答「還有沒有沒補完的」。

### (c) commit message 引用 spec 條款編號

```
feat(§2.1): 帳號首次登入強制改密碼
```

`git log` 就等於「規格條款實作史」。若某條 spec 條款被推翻，git 上能追到當初實作的 commit + 後來推翻的 commit，兩者一起看就是完整故事。

## 三份檔案的心智模型（下個專案）

- **spec.md**：**要做什麼 + 已做到哪**（權威事實）
- **CLAUDE.md**：**怎麼協作 + 架構規範**（不變的規則）
- **handoff.md**：**當前 session 的短期記憶**（哪一條 spec 正在做、下一步、暫時的疑問）——會**大幅瘦身**，因為「已完成、已定案、已知缺口」都在 spec 那邊了

下個專案的 handoff 想像只有 30-50 行：

```
最後更新：YYYY-MM-DD
當前工作：§3.2 主管作廢已核准單
下一步：驗證 D、更新 spec §3.2 打勾、commit
待決：§3.2 作廢時要不要順帶自動作廢結清紀錄？（見 issue #12）
本 session 疑問：無
```

## SDD 最容易踩的坑

**spec 寫太細、變成完整文件寫完才動 code**——這是 waterfall，不是 SDD。**規格書要跟開發同步演化**：第一版 spec 可能只有 §1 詞彙 + §2.1 帳號登入，做完再擴 §2.2、§3.1 …。這樣 spec 永遠是「已做到哪 + 下一步要加什麼」的活文件。

Amber 這次 vibe coding 反覆做的「先確認方向再動」——那個「方向」寫下來就是 SDD 的 spec 條款草稿。已經在做 SDD 的一半動作了，差的只是有沒有落成 spec.md 這個檔案。

## 下個專案開場時的行動清單（結案時再檢視）

- [ ] 開場先建 `spec.md` 骨架（§1 詞彙、§2 帳號、§3 報銷單 …），空的沒關係
- [ ] CLAUDE.md 修「session 開始先讀什麼」的規則——加「先讀 spec.md 找當前工作」
- [ ] handoff.md 縮到「當前工作 + 下一步 + 待決」三塊
- [ ] 決策紀錄拆到 `docs/decisions/` 或直接進 spec 的「已推翻」章節
- [ ] 開發環境獨立成 `docs/dev-environment.md`
- [ ] 驗證軌跡獨立成 `docs/verification-log.md`
- [ ] 每個 commit message 加 `(§X.Y)` 引用 spec 條款
- [ ] 在 handoff 或 CLAUDE.md 頂端加「開工前自檢清單」
