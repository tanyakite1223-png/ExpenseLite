## Handoff 的痛點(從讀取者實際體驗抓,不是從理論推)

1. **檔案讀不完整** —— Claude 第一次 Read 就撞到 32540 tokens 超過 25000 上限,必須分兩段讀。一份規範要求「每次 session 開頭讀」的檔,AI 讀不完整。
2. **同一件事寫 5-6 次,不確定「讀夠了沒」** —— 讀到第三次同主題時開始 mental cross-reference,判斷成本每次讀都要付一次。
3. **紅線埋在中後段**(299/356/422 行)—— 「不要再提議自助註冊」「不要提議零用金當預支款」「別復原 fixture 那張單」都要讀 400+ 行才碰得到。
4. **「下一步」在 490 行**,前面 480 行全是歷史 —— 「這次進來要幹嘛」的答案被歷史推到底部。
5. **不知道要不要再讀 `/docs/architecture/`** —— 〈邏輯落點〉那 40+ 行是縮略版理由,CLAUDE.md §4.9 說架構理由該住 architecture,那到底要不要再開檔看?讀取者要自己判斷。
6. **「見〈某章節〉」錨點找不到** —— 引用目標常常不是乾淨 h2/h3,而是某個 bullet 或散文中的關鍵字,要 grep 才找得到。
7. **一次讀完後下次仍要重讀** —— 疑難排解 11 條、fixture UUID 30 行、邏輯落點 40+ 行,單次讀完不代表下次可跳過,永遠是必讀路徑的一部分。

## 讀 user-accounts.md 進一步的觀察

這篇寫得很好,是 CLAUDE.md §4.9 要的樣子(主題聚焦、有推翻紀錄、有 tradeoff、有老實記著的限制)。**但幾乎完整地跟 handoff 打了兩份**——13 個對應點,同一件事兩處都寫完整版。

證明的事:**「已搬出去的東西沒有真的離開」**——handoff 不肯放手是主要病灶,不是 architecture 檔寫錯。

## 對「所有東西都往這檔塞是嚴重做法」的精確化

- **不是「塞太多」危險**
- **是「不區分讀取模式地什麼都塞進同一份必讀檔」危險**

這份檔同時想扮演兩種角色:

- **必讀檔**:薄、只有「現在做什麼 + 不能踩什麼」,每次開場快速讀完
- **可查詢資料庫**:厚、有全部細節,但只在需要時查

兩者的維護節奏、篇幅期待、讀取模式**完全相反**。代價:讀取者要花「當必讀檔的力氣」讀完「可查詢資料庫的尺寸」。

**成本會被規範放大**——「每次 session 開頭要讀」不是選擇性動作,這份檔的膨脹會直接乘上「未來 session 數量」變成累積成本。每加一段就等於未來每個 session 開場都多讀一段,沒有天花板。

## 業界框架:Diátaxis(核心發現)

網址:**[diataxis.fr](https://diataxis.fr)**

最主流、直接對應這個問題。GitLab / Cloudflare / Django / NumPy 官方文件都用。核心主張:**按讀者意圖分,不按主題分**。

四類:

| 類型 | 目的 | handoff 對應 |
| --- | --- | --- |
| Tutorial | 學習(給新手照著走) | 沒有,合理 |
| How-to guide | 解決具體問題(撞到時查) | 疑難排解那類 |
| Reference | 查資料(冷靜、結構化) | 已完成、pattern、決策結論 |
| Explanation | 理解為什麼(理由、tradeoff) | 邏輯落點、決策理由 |

**核心 heuristic**(比 CLAUDE.md 的抽象規則好用):
> "一段內容同時屬於兩類 = 有兩段內容纏在一起"

**Reference 的準則(Diátaxis 原話,順帶解 handoff 病)**:
> "Reference material should be austere, cool, factual, and structured for scannability. The most frequently needed information should be at the top."

**經典比喻**:
> "Reference is like a map. Explanation is like a travel guide. Trying to be both is trying to be neither."

## 其他參考

- **DITA (Darwin Information Typing Architecture)** —— OASIS 標準,更老、企業級,IBM 為主推。強制 Task / Concept / Reference 三型。
- **《Every Page is Page One》** —— Mark Baker, 2013。整本書講「為什麼書本式線性文件不適合線上」。
- **《Docs Like Code》** —— Anne Gentle, 第 2 版 2017。把文件當程式管:PR 更新對應文件、跟 code 住同 repo、走 review 流程。

「什麼時候該拆一份檔」的**具體行數/大小數據**:**業界沒有可靠共識**。多數是啟發式(涵蓋多概念就拆、讀者要跳到另一頁才懂前提就合)。Diátaxis 的答案是「用類型判斷,不用大小判斷——類型分對了,大小通常自然合理」。

## 用 Diátaxis 標 handoff 的 6 個混類病灶

| 病灶 | 位置 | 症狀 |
| --- | --- | --- |
| **A** | 〈已完成功能〉 | reference 塞 explanation(**重複幾十次**——每個功能都寫實作細節) |
| **B** | 〈已定案的設計決策〉每節 | reference + explanation 混寫,理由縮略版重複 architecture 檔 |
| **C** | 〈架構狀態 / 邏輯落點〉40+ 行 | **純 explanation 塞在 reference 檔**(該全刪,已經住 architecture 檔) |
| **D** | 〈疑難排解〉11 條 | how-to 混 explanation(前半問題、中間原因、後半解法) |
| **E** | 〈待 Amber 決定 / 下一步〉 | checkbox 混 explanation(每個打勾旁邊都補一段理由) |
| **F** | 頂端「最後更新」 | reference(commit list) 寫成 explanation(密集散文) |

估計:全部收乾後 **handoff 從 537 行 → 100-150 行**(-70%)。

## Diátaxis 對「原本沒解問題」的評估

前面 Claude 判斷四個「沒解」的問題,用 Diátaxis 重評:

| 原本沒解的問題 | Diátaxis 幫到嗎 |
| --- | --- |
| 執行紀律 | **幫到**——四類互斥好判斷,判斷成本降低。仍要人自己審視,可加 CI 檢查 hedge words 或大小限制當物理阻力 |
| 主題演化 / 拆檔時機 | **解掉**——新主題按四類拆解,不需為單一功能開新檔。碎片化壓力消失 |
| 檔案間錨點難找 | 只幫 30%——heading 命名會自然穩定,但「引用只指 heading」仍要另立紀律 |
| 紅線與下一步位置(單檔內) | **解掉**——Diátaxis 對 reference 檔明確要求「按查詢頻率排,不按時間排」 |

**意外順帶解的兩個**:
- AI token 上限撞牆 → explanation 拆出去後自動縮小
- handoff-archive 膨脹曲線(2 KB → 67 KB) → 只留 reference 後曲線會天然平

**唯一真正沒解的**:「引用一律指 heading 而非散文關鍵字」——需要獨立立紀律或 CI 檢查。

## Claude 提的分檔方案(僅供未來新專案參考,本專案不重寫)

| 檔案 | 職責(回答什麼問題) | 讀取模式 | 大小限制 |
| --- | --- | --- | --- |
| `START-HERE.md` | 現在做什麼 + 不要踩什麼 | **每 session 必讀** | **硬性 <100 行** |
| `CLAUDE.md` | 怎麼協作 + 架構規範 | 讀熟就免讀 | 現況 OK |
| `spec.md` | 做了什麼 / 還沒做什麼(checkbox 索引) | 查「做過了嗎」時讀 | 按模組分節 |
| `architecture/*.md` | 怎麼做 / 為什麼這樣做 | 動到相關功能時讀對應一份 | 現況組織對 |
| `troubleshooting.md` | 撞到怪事怎麼辦 | 撞到才查 | 主題分節 |
| `dev-environment/*.md` | 新機器要設什麼 | 換機器時讀 | 現況 OK |
| `verification-log.md` | 這條側門試過了嗎 | 追某功能有沒測時讀 | 只加不改 |

**核心原則**:每份檔對應**一種問題型別**,不是一個主題。

跟前一份 notes 比:多了 troubleshooting / verification-log / dev-environment 三塊獨立出來——因為它們才是佔 handoff 篇幅最多的「按需查」內容,不獨立出去,START-HERE 還是會被拖胖。

## 已確定的格式規則(可以拿來推廣)

- **連結顯示文字只放節名,不重複檔名**
  - ✅ `[首次登入強制改密碼](../docs/architecture/user-accounts.md#首次登入強制改密碼)`
  - ❌ `[user-accounts.md#首次登入強制改密碼](...)` —— 檔名重複
- **保留日期** `(2026-08-16)` —— git blame 可查,但保留能一眼看到「這是最近的東西」
- **引導詞**:
  - **一般位置** → `—— 詳見 [節名](錨點)`
  - **〈邏輯落點〉區** → `—— 〈邏輯落點〉見 [節名](錨點)`(告訴讀者這條在 handoff 哪一區、要看的目標理由在哪)
- **錨點格式(GitHub 規則,已實測可連)**:
  - 中文保留,全形引號 strip 掉
  - 例:`### 順帶擋掉「主管對自己動」` → `#順帶擋掉主管對自己動`
  - 例:`## 首次登入強制改密碼` → `#首次登入強制改密碼`

### 親身觀察(筆記沒寫的)

1. **第一次 Read handoff 就撞 25000 token 上限**——實際體驗,不是聽說。原本痛點仍在。
2. **grep 一輪抓不齊分佈**——用「日常主管」漏了邏輯落點段的 `CountActiveDailyManagersAsync`(英文 method 名),第二輪 grep 才找到。**掃分佈不是一次 grep 能可靠完成的工作**——這對推廣是個實際成本。
3. **主題大小差異大,外推不成立**——這輪「只剩一位日常主管」4 處只減 -294 bytes;昨天「首次登入強制改密碼」5 處減 -1,708 bytes。**「10 個主題 × 平均 = 目標」的算法不可靠**,筆記推估 -70% 是樂觀。
4. **頂端 1 處單點槓桿最大**——頂端 -603 bytes,比整個「只剩一位日常主管」4 處還多。**如果只能做少數改動,先動頂端 CP 值最高**——這是實作後才看出來的優先順序。
5. **頂端 refactor 沒解「下一步在 490 行」病灶**——Diátaxis 說 Reference 該把最頻繁需要的放頂端。「下一步」是最頻繁的,仍在 490 行。**頂端變成 meta 資訊區,不是 action 區**。這個病灶沒動到。
6. **列印報表撞到「頁面規格該住哪」是實際卡點**——不是理論議題。單一議題不決定,**整個 pipeline 就卡在第 2 個主題**。這個 fragility 筆記沒抓到。
7. **同檔多處 Edit 並行可行**——4 個 Edit 同 message 全成功,不用循序做。

### Session 內產生的新框架(筆記沒有)

- **訊號質變 vs 量變**:「只剩一位日常主管」-0.4%,但**質變**是 handoff 對這件事從「重複 explanation」變「做了/去哪查」。筆記只算 bytes 是漏了這維度。
- **候選進度 tri-state 追蹤**:「1/7 完成、1/7 擱置、5/7 沒動」比「還沒做完」精確,擱置跟沒動性質不同。
- **「收乾實驗完成」vs「handoff 檔更新」是兩層**——這 session 從 Amber 問「handoff 也做完了嗎」才顯化這個區分。應該進方法論。
- **架構檔涵蓋度要逐主題實際對照**——不能預設「已有 architecture 檔就 OK」。列印報表反證:architecture 檔涵蓋 explanation 但沒 cover 頁面規格 reference。

### 對 SDD 的實質輸入(從實際操作提煉,不是理論)

- 掃分佈需**多輪不同關鍵字組合 grep**(單一詞抓不齊)
- 主題大小差異大,**用 bytes / 處數推估總量不可靠**,要逐主題實測
- 頂端 CP 值最高,**先動頂端**
- **收乾實驗跟 handoff 頂端更新是兩層動作**,別混
- 遇到 architecture 檔涵蓋不全時,要有**明確原則**(要不要搬、搬哪去),否則單議題卡整條 pipeline

### 待續議題

- 頂端 refactor 沒解「下一步在 490 行」——要怎麼解?
- 列印報表的「頁面規格該住哪裡」原則——不決定就卡住 pipeline
- Q1 剩 5 個歷史主題要不要繼續(報銷單生命週期擴充、預支款收斂、緊急存取帳號、不刪使用者、審核人 ≠ 申請人)
