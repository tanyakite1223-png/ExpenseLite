# 預支款為什麼獨立成 CashAdvance

本專案把「預支款」做成 `CashAdvance`，不是只在報銷單上放一個文字欄位。原因是出納月底核帳時，需要知道公司先給了誰多少錢、哪些已經被核准報銷單核銷、還差多少沒有對上。

`ExpenseReport` 仍然是報銷單 aggregate root，明細只能透過報銷單新增或移除。預支款則是另一個 aggregate root；報銷單如果是個人預支，只保存 `CashAdvanceId` 這個 ID 參照，不直接持有或修改整個 `CashAdvance` 物件。

目前範圍刻意只做到「可追蹤、可核對、可查未結清」：

- 預支款記錄領款人、用途、日期、金額。
- 報銷單的付款方式三選一：員工墊款 / 個人預支 / 零用金支付。
- 只有個人預支報銷單要連到一筆預支款，其餘兩種都不連。
- 預支款列表用已核准報銷單加總核銷金額，顯示差額。
- 若核准報銷金額與預支金額不同，可在預支款底下新增實際結清紀錄：公司補付或員工繳回。

結清紀錄做成 `CashAdvance` aggregate 內部 entity，不單獨建立 repository。原因是它沒有獨立生命週期：它只是在說「這筆預支款後來實際補付 / 繳回多少」，所以新增紀錄一律走 `cashAdvance.AddSettlementRecord(...)`。

但「目前到底還要補付或繳回多少」不是 `CashAdvance` 自己能單獨知道的事，因為它需要同時查詢已核准的 `ExpenseReport`。因此本專案把差額與尚待結清金額放在 `CashAdvanceAppService` 組 DTO 時一起計算，Domain entity 只守住單筆結清紀錄的基本規則，例如結清金額必須大於 0、處理人不可空白。

後續補上修改 / 標記為不採用時，仍然維持同一個 aggregate 邊界：修改與不採用都透過 `CashAdvance` root 操作，不讓外層直接改 `CashAdvanceSettlementRecord`。不採用不是從資料庫刪除，而是保留處理人、原因與時間；列表核對金額只加總仍被採用的紀錄，詳情頁仍能看完整歷史。

預支款本身可修改用途與金額，但金額修改會影響差額與應結清金額，所以只允許在「尚未被任何報銷單引用、也沒有已計入核對的結清紀錄」時修改。結清紀錄是否已計入核對屬於 `CashAdvance` aggregate 內部規則；是否已有報銷單引用則是跨 aggregate 查詢，放在 `CashAdvanceAppService` 判斷。

## 為什麼零用金不是預支款

這一節是本專案唯一一次**推翻自己做完的模型再重做**，值得留著。

一度為了支援零用金，我們在 `CashAdvance` 上加了 `CashAdvanceUsage` 欄位（`Personal` / `PettyCash`），讓「零用金」這種預支款可以被所有人的報銷單引用。實作是通的、畫面也做得出來，但模型是錯的。

錯在**兩者是不同的東西**：

| | 預支款 | 零用金 |
| --- | --- | --- |
| 這筆錢是什麼 | 公司先撥給**某個人**的錢 | 由保管人看管的一筆**定額基金** |
| 會計上的意義 | 對那個人的應收款 | 公司的現金，只是放在抽屜裡 |
| 有幾個當事人 | 一人一筆，不可能共用 | 全公司都跟同一個抽屜拿錢 |
| 會結束嗎 | 會，多退少補之後就結清了 | 不會，花掉就補回來，額度不變 |

把它們放進同一條核對算式必然算錯。核對算的是 `差額 = 已核准報銷 − 預支金額`，這條式子只在「這筆錢是預先給某個人、之後要跟他算清」時才成立。套到零用金上，大家報滿額度時系統會判定「已結清」——但現實中那正是抽屜空了、該補撥現金回去的時刻。**方向剛好相反。**

真實資料也證實了這件事：舊資料裡 7 筆被當成零用金的預支款，有 3 筆確實被三個不同的人開單引用，而且報銷總額都遠超過預支金額——核對表因此顯示「公司需補付 780 給某某」這種語意上根本不成立的數字。

### 收斂後的樣子

- **`CashAdvance` 收斂成一人一筆的個人預支**，`CashAdvanceUsage` 整個移除。
- **零用金改成報銷單的一種付款方式**，不是一筆資料。`ExpensePaymentMethod` 因此變成三選一，分類依據是**錢從哪來**：

  | 付款方式 | 錢從哪來 | 公司事後還要付錢嗎 | 綁預支款嗎 |
  | --- | --- | --- | --- |
  | `EmployeePaid`（員工墊款） | 設計師自己的錢 | 要，付錢還他 | 否 |
  | `PersonalAdvance`（個人預支） | 公司事先給他的錢 | 多退少補 | **是** |
  | `PettyCash`（零用金支付） | 零用金抽屜 | 不用，當場就付掉了 | 否 |

- **抽屜裡的現金餘額不進系統**，由保管零用金的人自己記錄。系統只做「標記 + 事後篩選統計」——報銷單列表既有的付款方式篩選就能撈出「這期間零用金花了多少」。

### 模型對了的訊號：規則從兩條變一條

收斂前 `ExpenseReport.EnsureBasicInfoIsValid` 是兩條對稱的規則（預支費用必須綁、員工墊款不可綁）。加了第三個付款方式之後，規則反而**變少**：

```csharp
// 只有個人預支要綁預支款；員工墊款與零用金支付的錢都不是預先撥給某個人的，所以都不綁。
if (paymentMethod == ExpensePaymentMethod.PersonalAdvance && cashAdvanceId is null)
    throw new DomainRuleViolationException("個人預支報銷單必須選擇對應的預支款。");

if (paymentMethod != ExpensePaymentMethod.PersonalAdvance && cashAdvanceId is not null)
    throw new DomainRuleViolationException("只有個人預支報銷單可以連到預支款。");
```

**選項變多、規則變少，通常代表切分對上了現實的關節。** 反過來說，如果當初硬把零用金留在 `CashAdvance` 裡，每加一個情境就要多一條 `if`，那是模型不對的訊號。

### 老實記著這個簡化的限制

本專案已定案不做會計帳，所以系統裡沒有「付款」這個動作。「零用金支付」目前**只是一個標記，後面沒有任何行為掛在上面**。它的價值在於主管審核時看得出這張單不用再付錢、以及事後篩選統計。這是刻意取捨，不是缺陷。

## 領款人：為什麼存 UserId + 姓名快照，且建立後不可修改

領款人一開始只是手動輸入的字串。加上登入功能之後改成 `PayeeUserId`（Guid）+ `PayeeName`（姓名快照），比照報銷單申請人的慣例——UserId 給程式比對，姓名是寫入當下的快照，日後改名不改寫歷史。舊資料沒有帳號可對應，所以 `PayeeUserId` 是 nullable。

領款人**不會**自動帶入登入者，這跟申請人、審核人、結清處理人相反。差別在於領款人是「當事人」不是「操作者」：主管很可能替員工建立一筆預支款。所以建立表單是一個使用者下拉，由主管挑人。

姓名快照由 `CashAdvanceAppService.CreateAsync(...)` 自己查 `IUserDirectory` 取得，**不接受表單送進來的字串**，避免有人竄改表單讓紀錄上的名字跟帳號對不上。

`CashAdvance.UpdateBasicInfo(...)` 只接用途說明與金額，刻意不接領款人——換掉領款人等於改寫「這筆錢當初給了誰」。這跟 `ExpenseReport.UpdateBasicInfo(...)` 不接申請人是同一個道理：**有些欄位是「這筆資料的身分」，不是可編輯的內容。**

### 「誰能引用這筆預支款」是模型規則，不是權限

報銷單的預支款下拉只列出領給你自己的預支款：

```csharp
private static bool CanBeReferencedBy(CashAdvance cashAdvance, CurrentUser viewer)
    => cashAdvance.PayeeUserId == viewer.UserId;
```

注意這條**不是授權**：換一個角色答案不會變，連主管都不能拿別人的預支款來報自己的單。授權的定義是「同一份資料，不同人能做的事不一樣」；這裡是「這筆錢本來就是那個人的」，跟誰在操作無關。對照組是同一個 service 裡的 `CanBeViewedBy(...)`——那條才是授權，因為主管看得到全部、員工只看得到自己的。

為什麼放在 `CashAdvanceAppService` 而不是 entity：這是在「挑出可選項目」，本質是查詢與呈現，`CashAdvance` 自己不需要知道有誰在看它。

## 其他

同一筆預支款只要還有 Draft / Submitted / Returned 的關聯報銷單，系統只顯示暫估核對，暫不允許新增最終結清紀錄。這是為了避免流程中的報銷單後續核准後改變應補付 / 應繳回方向。

這裡仍然沒有做完整會計總帳，也刻意不支援沖銷、付款憑證或真正的出納日記帳。若之後要進入會計帳範圍，再另外設計，不把第一階段做得過重。
